Aide

Comment ça marche

Une demande de VM part d'une des deux sources possibles, indépendantes l'une de l'autre :

  • Webhook GLPI (/webhooks/glpi) — un ticket créé via un formulaire GLPI Formcreator
  • Formulaire natif (Création de VM ▾ → Nouvelle demande) — directement dans l'app, si activé ci-dessous

Les deux créent exactement la même chose en interne et suivent ensuite le même circuit :

  1. Validation humaine — un admin approuve ou rejette depuis Création de VM ▾ → En attente. Rien ne se crée tant que personne n'a validé.
  2. Réservation IP — l'IPAM actif (phpIPAM aujourd'hui) réserve une IP statique, jamais de DHCP pour un serveur.
  3. Création de la VM — Terraform clone le template choisi sur le cluster Proxmox.
  4. Post-install Ansible — compte admin + clé SSH déployés, accès root fermé en SSH, puis les playbooks du catalogue sélectionnés à l'approbation.
  5. Notification — si la demande vient de GLPI, un commentaire est posté sur le ticket à chaque étape (approbation, rejet, fin). Silencieusement ignoré sinon.

Ce que tu peux faire

  • Connexions (/connections) — Proxmox, phpIPAM, GLPI, dépôt Git de playbooks, LDAP. Chaque formulaire a un bouton "Tester la connexion" qui dit précisément ce qui ne va pas (hôte injoignable, identifiants refusés...).
  • Catalogue de playbooks (/playbooks) — ajoute tes propres playbooks (chemin dans ton dépôt Git), choisis s'ils sont obligatoires ou optionnels à l'approbation.
  • Déploiement à la demande (/playbooks/deploy) — relance un playbook contre n'importe quel hôte de ton inventaire, pas seulement les VMs créées par ce pipeline. Mode "dry-run" disponible pour simuler sans rien changer.
  • Inventaire (/playbooks/inventory) — groupes et hôtes gérés depuis l'interface, ou régénérés automatiquement depuis la découverte Proxmox.
  • Sous-réseaux IPAM par VLAN — sur une connexion phpIPAM, plusieurs VLAN/sous-réseaux possibles (/connections/<nom>/subnets), résolus automatiquement selon le VLAN de la demande.
  • HTTPS (/settings/tls) — certificat auto-signé en un clic, ou importe le tien.
  • Utilisateurs (/settings/users) — comptes locaux ou LDAP, rôles admin/lecture seule, réactivation d'un compte verrouillé.
  • Journal d'audit — connexions et requêtes, dans /app/logs/audit.log (pas encore de vue dans l'interface — fichier à consulter via docker compose exec backend tail -f /app/logs/audit.log).
